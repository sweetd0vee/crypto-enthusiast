# Минутный ТВ-опрос

### Анонимное голосование во время ТВ-эфира

Принять массовый пик, отклонить обычные повторы и показать обезличенный
результат.

> Redis принимает пик, PostgreSQL сохраняет правду.

---

# 2. Задача

100 млн голосов за 60 секунд — теоретически около **1,7 млн RPS**. Это не
результат локального теста, а ориентир для архитектуры.

- **Быстро:** не обращаться к SQL на каждом голосе.
- **Надёжно:** не считать повтор и уметь восстановить итог.
- **Приватно:** не требовать регистрацию и не хранить сырой IP.

---

# 3. Архитектура

```text
Зрители ─► Nginx ─► FastAPI ─► Redis
                       │       ├─ кэш вопроса
Администратор ─────────┤       ├─ дедупликация
                       │       └─ live-счётчики
                       ▼
                  PostgreSQL
                  ├─ вопросы
                  ├─ журнал голосов
                  └─ итоговые снимки
```

- Redis поглощает короткий массовый пик.
- PostgreSQL остаётся источником правды.
- Stateless API можно масштабировать горизонтально.

---

# 4. Как принимается голос

1. API получает вопрос, вариант и cookie `vid`.
2. Проверяет статус, временное окно и вариант.
3. Вычисляет хеш `question_id + vid`.
4. Lua атомарно проверяет dedup и увеличивает счётчик.
5. Новый голос получает `201`, повтор — `409`.

`SET NX + HINCRBY` выполняются одной операцией — частично принятого голоса нет.

---

# 5. Демонстрация проекта

**Место для видео продолжительностью 60–90 секунд**

1. Администратор создаёт и публикует опрос.
2. Зритель переходит по QR и голосует.
3. Результат обновляется в реальном времени.
4. Повторный голос отклоняется.

---

# 6. Данные и результаты

**Redis:** карточка вопроса, dedup с TTL, шардированные счётчики.

**PostgreSQL:** вопросы, варианты, журнал голосов, итоговые снимки.

Live-результат читается из Redis. Если оперативные счётчики потеряны,
результат закрытого опроса пересчитывается из журнала PostgreSQL.

Cookie `vid` идентифицирует браузер, а не человека. Сырой IP не хранится.

---

# 7. Проверка качества

- unit-тесты backend;
- lint и сборка Python/TypeScript;
- HTTP acceptance-сценарии;
- Playwright E2E в Chromium.

Критические проверки: параллельный повтор, неверный вариант без записи,
два браузера за одним IP и восстановление результата.

Полный набор запускается командой `make verify`.

---

# 8. Итог

**Готово:** full-stack MVP, Docker, live-результаты и автотесты.

**Ограничения MVP:**

- масштаб нужно подтвердить нагрузочными тестами;
- cookie dedup не защищает от профессионального бота;
- async-журнал нужно вынести в durable queue;
- для production нужны OIDC, RBAC и наблюдаемость.

> MVP демонстрирует правильные архитектурные границы.
