# Разбор задачи и кода

Этот файл для человека, который впервые открыл репозиторий. Здесь задача
пересказана обычным языком, а затем те же действия прослежены по файлам:

## Задача своими словами

Компания проводит опросы в минутном телеролике. На экране один вопрос и
QR-код. Зритель наводит камеру, открывает страницу и нажимает один вариант.
Регистрации нет: имя, почта и пароль не спрашиваются.

Ролик короткий, аудитория огромная. В условии — около 100 миллионов зрителей
за минуту. Даже если проголосует меньшая доля, сервер в эту минуту получает
очень много одинаковых коротких запросов и почти не получает запросов от
админов.

Нужны три возможности:

1. Зритель открывает вопрос и голосует без аккаунта.
2. Админ создаёт вопрос, меняет его и при необходимости удаляет.
3. Админ видит суммы по вариантам. В этих суммах нет IP, cookie и других
   следов конкретного человека.

Повтор с того же браузера не должен увеличивать счётчик. Защита нарочно
простая: её хватает против обычного зрителя, который нажмёт кнопку дважды.
Инкогнито, другой браузер и сброс cookie обходят её, и это принимается.

## Два действующих лица

| Кто | Что делает | Куда попадает |
| --- | --- | --- |
| Зритель | Открывает ссылку с QR и выбирает вариант | Страница `/q/123`, запросы без токена |
| Админ | Заводит вопрос и смотрит суммы | Страницы `/admin` и `/admin/questions/123`, заголовок `Authorization: Bearer <токен>` |

Локальный токен — `dev-admin-token`. Он лежит в переменной `ADMIN_TOKEN` и
сравнивается с заголовком в `require_admin()` (`backend/app/api/deps.py`).
Полноценных пользователей и ролей в проекте нет.

Ссылка для зрителя в интерфейсе — `/q/123`. Браузер рисует её компонентом
`ViewerPage`. Сам API живёт на других путях: `GET /questionnaire/123` и
`POST /questionnaire/123/votes`. Nginx и Vite проксируют эти пути на backend,
поэтому страница и API для браузера выглядят одним сайтом. Так cookie
зрителя остаётся на том же сайте.

## Почему два хранилища

PostgreSQL хранит то, что должно пережить перезапуск и что читают редко:

- текст вопроса и варианты (`question`, `question_option`);
- журнал принятых голосов (`vote`);
- снимок сумм после пересчёта (`question_result`).

Redis хранит то, к чему обращается каждый голос в минуту эфира:

- карточку вопроса, чтобы не ходить в PostgreSQL на каждый клик;
- отметку «этот браузер уже голосовал»;
- счётчики вариантов.

Голос принимается в Redis. Строка журнала в PostgreSQL пишется следом.
Дашборд во время эфира складывает счётчики Redis и не делает `COUNT(*)` по
миллионам строк.

Если Redis в минуту эфира недоступен, голосование отвечает `503`. Записать
голос сразу в PostgreSQL в этот момент нельзя: отметка «уже голосовал» и
счётчик разъедутся.

## Как разложен код

```text
backend/app/
  main.py              процесс стартует и гаснет здесь
  config.py            переменные окружения
  api/                 HTTP: маршруты, токен, формат ошибок
  question/            создание и правка вопроса
  vote/                страница зрителя и приём голоса
  result/              суммы для админки
  store/               подключения к PostgreSQL и Redis, имена ключей, таблицы

frontend/src/
  App.tsx              какие URL открывают какие страницы
  api.ts               все вызовы backend из браузера
  pages/               экран зрителя, вход, список вопросов, результаты
```

Слои backend разделены так:

1. Файл в `api/` принимает HTTP, достаёт cookie и тело JSON и вызывает сервис.
2. Файл в `question/`, `vote/` или `result/` решает, можно ли это сделать,
   и пишет в базу или Redis.
3. Файл в `store/` знает, как называются таблицы и ключи Redis.

Обработчик маршрута сам SQL не пишет. Если правило нарушено, сервис
бросает `AppError` с кодом вроде `already_voted`. `backend/app/api/errors.py`
превращает её в JSON `{"error": "...", "message": "..."}`.

## Что происходит при старте

`backend/app/main.py`, функция `lifespan()`:

1. Читает настройки (`DATABASE_URL`, `REDIS_URL`, токен, число шардов).
2. Открывает пул соединений к PostgreSQL.
3. Открывает клиент Redis.
4. Создаёт журнал голосов. При `VOTE_ASYNC=true` запускает фоновую задачу,
   которая пачками пишет строки в PostgreSQL.
5. Отдаёт управление FastAPI и начинает принимать запросы.
6. При остановке дожидается журнала и закрывает оба клиента.

`GET /healthz` пингует оба хранилища. Оба живы — `200`. Любое из них молчит —
`503`.

Один процесс API ничего не помнит у себя в памяти между запросами. Карточка,
отметка и счётчики лежат в Redis, поэтому несколько копий API могут работать
параллельно.

## Жизнь вопроса

В базе у вопроса три сохранённых статуса: `draft`, `published`, `cancelled`.
Ещё три статуса на экран считаются из часов сервера и в базу не пишутся.
Это делает `effective_status()` в `backend/app/question/models.py`:

| Что видит админ | Откуда берётся |
| --- | --- |
| `draft` | Вопрос сохранён как черновик |
| `cancelled` | Вопрос отменён |
| `scheduled` | Опубликован, серверное время ещё меньше `show_time` |
| `live` | Опубликован, время внутри окна |
| `closed` | Опубликован, окно уже закончилось |

Окно — полуинтервал `[show_time, show_time + duration_seconds)`. В начале
этой секунды голосовать можно, в секунду закрытия — уже нельзя. Часы телефона
зрителя не участвуют: сравнение делает сервер.

Опубликованный вопрос обязан иметь `show_time`. Вариантов от 2 до 10, ключи
внутри одного вопроса уникальны. Длительность — от 10 до 3600 секунд,
по умолчанию 60.

Черновик зрителю не отдаётся. Вопрос, по которому уже есть голоса, нельзя
удалить и нельзя поменять у него набор вариантов: иначе старые счётчики
указывали бы на исчезнувшие кнопки.

## Сценарий 1. Админ создаёт вопрос

Браузер открывает `/admin`. `RequireAuth` смотрит, есть ли токен в
`sessionStorage`. Токена нет — переход на `/admin/login`. После входа токен
хранится только в этой вкладке браузера.

`AdminPage` при открытии вызывает `api.listQuestions()`. Функция
`adminRequest()` в `frontend/src/api.ts` добавляет заголовок
`Authorization: Bearer ...` и идёт на `GET /questions`.

На backend маршрут описан в `backend/app/api/admin.py`. Весь роутер висит на
`require_admin()`, поэтому каждый такой запрос сначала сверяет токен.
Дальше `list_questions()` читает вопросы и варианты двумя SQL-запросами и
собирает ответ в памяти.

Сохранение формы идёт в `create_question()` (`backend/app/question/service.py`):

1. В одной транзакции вставляется строка `question`.
2. Рядом вставляются строки `question_option`. Поле `position` — это порядок
   кнопок на экране.
3. Транзакция фиксируется.
4. После commit карточка кладётся в Redis по ключу `question:{id}`.

Зритель во время эфира читает эту карточку из Redis. Пока кэш пуст, первый
запрос читает PostgreSQL и заполняет Redis. У карточки нет срока жизни:
создание и правка перезаписывают её, удаление стирает ключ.

## Сценарий 2. Зритель открывает QR и голосует

Адрес в браузере: `/q/123`. Его рисует `ViewerPage` (`frontend/src/pages/ViewerPage.tsx`).

### Открытие страницы

`useEffect` вызывает `api.getPublicQuestion('123')`. Это `GET /questionnaire/123`.
Маршрут — `questionnaire()` в `backend/app/api/public.py`.

Дальше по шагам:

1. `_viewer_id()` смотрит cookie `vid`. Если там корректный UUID, он
   используется снова. Если cookie нет или она испорчена, сервер придумывает
   новый UUID.
2. `get_public_question()` в `backend/app/vote/service.py` загружает вопрос
   через `_load_question()`: сначала Redis, при промахе PostgreSQL.
3. `require_open_voting_window()` из `question/voting_window.py` проверяет,
   что вопрос опубликован и серверное время внутри окна. Рано —
   `403 window_not_started`. Поздно — `410 window_closed`. Черновик —
   `403 not_published`.
4. Сервер проверяет, есть ли уже ключ «этот браузер голосовал». Есть —
   `409 already_voted`, кнопки не показываются.
5. Наружу уходит только `id`, `name`, `closes_at` и список `{key, label}`.
   Статус, внутренние хеши и время показа в этом JSON отсутствуют.
6. Если `vid` был новым, ответ ставит cookie: `HttpOnly`, `SameSite=Lax`,
   живёт сутки, путь `/`. JavaScript страницы эту cookie прочитать не может.
   Браузер сам приложит её к следующему запросу на тот же сайт.

`ViewerPage` по коду ошибки из `error` выбирает текст в `viewerMessages`.
Пока запрос идёт, состояние экрана — `loading`. Успех — `ready`, на экране
кнопки вариантов.

### Нажатие кнопки

`submit(option)` ставит состояние `submitting` и вызывает `api.vote(id, option)`.
Тело запроса — `{"option": "a"}`, где `a` — это `key` варианта, не подпись
на кнопке.

Маршрут `vote()` в `public.py` снова достаёт `vid` и IP соединения, затем
зовёт `accept_vote()`:

1. Снова загружает карточку и проверяет окно. Между открытием страницы и
   кликом окно могло закрыться.
2. Проверяет, что `option` есть среди ключей вопроса. Чужого ключа нет —
   `422 invalid_option`. Redis при этом ещё не меняется.
3. Считает `dedup_hash`: SHA-256 от строки `question_id|viewer_id`.
   В Redis ключ выглядит как `vote:123:<этот хеш>`.
4. Выбирает шард счётчика: `crc32(хеш) % COUNTER_SHARDS`. Локально шард один,
   ключ `results:123:0`. При нескольких шардах голоса одного вопроса
   разъезжаются по разным ключам Redis, чтобы один ключ не принимал всю
   страну. Чтение результата потом складывает их обратно.
5. Одним Lua-скриптом `ACCEPT_VOTE_SCRIPT` делает две записи атомарно.
   Скрипт изолирован в `vote/atomic_counter.py`.
6. Если отметка уже стояла, скрипт возвращает `0`, API отвечает
   `409 already_voted`.
7. Если голос первый, скрипт возвращает `1`. Сервер собирает `VoteEvent` и
   пишет его в журнал.

`VoteEvent` содержит номер вопроса, ключ варианта, хеш cookie, хеш IP и
время. Сырой IP в журнал не попадает: `client_ip_hash()` считает
SHA-256 от `ip|соль`. Соль — `IP_HASH_SALT`. Этот хеш нужен журналу и не
участвует в решении «пускать или нет». Два браузера за одним домашним
роутером имеют один IP и разные cookie, поэтому оба голоса принимаются.

### Что делает Lua

Redis выполняет скрипт целиком, без чужих команд посередине. Смысл скрипта:

1. Ключ отметки уже есть — вернуть `0` и ничего не менять.
2. Ключ счётчика должен отсутствовать или быть hash. Иначе скрипт
   останавливается с ошибкой, отметку не ставит.
3. Поставить отметку со сроком жизни: до конца окна плюс ещё сутки.
4. Увеличить поле выбранного варианта в hash на 1 (`HINCRBY`).
5. Вернуть `1`.

Две отдельные команды «поставь отметку» и «прибавь счётчик» могли бы
разорваться: процесс упал бы между ними, и человек оказался бы отмеченным
без голоса или наоборот. Один `eval` этого разрыва не оставляет.

Повтор того же запроса безопасен. Если сеть потеряла ответ, браузер может
послать голос ещё раз и получить `already_voted`: счётчик уже увеличен один
раз.

### Журнал после ответа Redis

При `VOTE_ASYNC=false` `journal.write()` сразу вставляет строку в `vote`.
При `VOTE_ASYNC=true` событие кладётся в очередь процесса. Фоновая задача
собирает до 1000 событий или ждёт 50 мс и вставляет пачку.
`INSERT ... ON CONFLICT DO NOTHING` глушит повтор той же пары
`(question_id, dedup_key)`, если строка уже есть.

Счётчик Redis при этом уже увеличен. Если запись журнала не удалась, голос
в сумме эфира есть, а строки в PostgreSQL может не быть. Это известное
ограничение текущей версии, оно записано в
[05-production-roadmap.md](05-production-roadmap.md).

`ViewerPage` после `201` показывает состояние `success`. Повторный заход с
той же cookie на открытии страницы получит `already_voted`.

## Сценарий 3. Админ смотрит суммы

Со страницы списка ссылка ведёт на `/admin/questions/123`. `ResultsPage`
вызывает `GET /questions/123/results`. Пока `effective_status` равен `live`,
страница повторяет запрос каждые 2 секунды.

`get_results()` в `backend/app/result/service.py`:

1. Читает вопрос из PostgreSQL, чтобы знать подписи вариантов и статус.
2. `_read_counters()` делает `HGETALL` по каждому шарду `results:{id}:{n}`
   и складывает числа в процессе API.
3. Если хотя бы один шард непустой, эти суммы и есть ответ.
4. Если шардов нет и вопрос уже не в эфире, вызывается `rebuild_results()`:
   `GROUP BY` по журналу `vote`, снимок в `question_result`, запись тех же
   чисел обратно в Redis.
5. Пока идёт эфир и счётчиков нет, пересчёт не запускается: пустой эфир
   остаётся нулями, дашборд не сканирует журнал на каждом обновлении.

Ответ — `question_id`, имя, статус, `total` и массив `{key, label, count}`.
Проценты считает уже браузер: `count / total`.

`POST /questions/{id}/results/rebuild` делает тот же пересчёт по кнопке
админа, когда Redis очистили или цифры нужно восстановить из журнала.

## Что можно менять после создания

`update_question()` блокирует строку вопроса в транзакции.

Набор вариантов сравнивается с текущим. Если ключи или подписи изменились,
`_has_votes()` смотрит две вещи: есть ли строка в `vote` и есть ли
положительное число в шардах Redis. Любой найденный голос даёт
`409 options_locked`.

Имя, время показа, длительность и статус по-прежнему можно менять, пока
набор кнопок тот же. После commit карточка в Redis перезаписывается.

`delete_question()` удаляет строку только у черновика без голосов. Опубликованный
вопрос и любой вопрос с голосами получают `409 delete_forbidden`. После
удаления ключ `question:{id}` из Redis стирается.

## Как устроен ответ с ошибкой

Сервис не собирает `JSONResponse`. Он бросает `AppError(статус, код, текст)`.
Например, повторный голос — это `AppError(409, "already_voted", "Вы уже проголосовали")`.

Клиент смотрит поле `error`, а человеку показывает `message`. Фронтенд
для зрителя ещё подменяет часть кодов короткими фразами из `ui.ts`.

Кривой JSON, пустое имя или неуникальные ключи вариантов FastAPI ловит
раньше сервиса и отдаёт `422 invalid_body`.
