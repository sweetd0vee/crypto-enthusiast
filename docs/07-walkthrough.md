# Разбор для первого чтения

Задача обычным языком и три сценария по файлам. Требования —
[01](01-specification.md), решения — [02](02-architecture.md), URL —
[03](03-api.md), файлы — [06](06-code-reference.md).

Компания показывает в минутном ролике один вопрос и QR. Зритель открывает
страницу и нажимает вариант. Имени, почты и пароля нет.

В условии около 100 миллионов зрителей за минуту. Даже если проголосует
меньшая доля, в эту минуту приходят одинаковые короткие запросы, а админка
почти молчит. Поэтому текст вопроса и журнал живут в PostgreSQL, а карточка,
отметка «уже голосовал» и счётчики — в Redis. Если Redis в эфире недоступен,
голос получает `503`: записать его сразу в PostgreSQL нельзя, дедуп и
счётчик разъедутся.

Нужны три возможности: анонимный голос, создание вопроса и обезличенные
суммы. Повтор с того же браузера не увеличивает счётчик. Инкогнито и сброс
cookie обходят защиту, и это принято.

| Кто | Куда попадает |
| --- | --- |
| Зритель | страница `/q/123`, запросы без токена |
| Админ | `/admin` и `/admin/questions/123`, заголовок `Authorization: Bearer <токен>` |

Локальный токен — `dev-admin-token`. Его сравнивает `require_admin()` в
`backend/app/api/deps.py`. Ролей нет.

Страницу рисует `ViewerPage`. API — `GET /questionnaire/123` и
`POST /questionnaire/123/votes`. Nginx и Vite проксируют эти пути, поэтому
для браузера сайт один и cookie остаётся same-site.

Слой `api/` достаёт cookie и JSON. Слой `question/`, `vote/` или `result/`
решает, можно ли это сделать. `store/` знает имена таблиц и ключей.
Нарушение правила — `AppError` из `backend/app/errors.py`.
`backend/app/api/errors.py` превращает её в
`{"error": "...", "message": "..."}`.

## Жизнь вопроса

В базе три статуса: `draft`, `published`, `cancelled`. Экранные
`scheduled`, `live` и `closed` считает `effective_status()` в
`backend/app/question/models.py` по часам сервера. Окно — полуинтервал
`[show_time, show_time + duration_seconds)`. Границу считает
`question/voting_window.py`. В секунду начала голосовать можно, в секунду
закрытия — уже нет.

Черновик зрителю не отдаётся. Вопрос с голосами нельзя удалить и нельзя
поменять у него набор вариантов: старые счётчики указывали бы на исчезнувшие
кнопки.

## Сценарий 1. Админ создаёт вопрос

`/admin` закрыт `RequireAuth`. Токен хранится в `sessionStorage` через
`adminAuth.ts` и живёт в этой вкладке. Нет токена — переход на
`/admin/login`. Сам токен проверяет первый запрос к API: `401` стирает его
и возвращает на вход.

`AdminPage` вызывает `api.listQuestions()` → `GET /questions`.
`list_questions()` читает вопросы и варианты двумя SQL-запросами.

`create_question()` в `backend/app/question/service.py`:

1. в одной транзакции вставляет `question` и `question_option`;
2. `position` — порядок кнопок;
3. после commit кладёт карточку в Redis по ключу `question:{id}`.

Пока кэша нет, первый запрос зрителя читает PostgreSQL и заполняет Redis.
Срока жизни у карточки нет.

Для `scheduled` и `live` в таблице есть QR. `QuestionShareDialog` показывает
ссылку `/q/{id}` и скачивает SVG. У черновика ссылки на результаты нет.

## Сценарий 2. Зритель открывает QR и голосует

Адрес `/q/123` рисует `ViewerPage`.

### Открытие

`api.getPublicQuestion('123')` → `GET /questionnaire/123` → `questionnaire()`
в `backend/app/api/public.py`.

1. `_viewer_id()` берёт cookie `vid`. Корректный UUID используется снова.
   Нет cookie или она битая — сервер делает новый UUID.
2. `get_public_question()` грузит карточку: сначала Redis, при промахе
   PostgreSQL.
3. `require_open_voting_window()` проверяет публикацию и окно. Рано —
   `403 window_not_started`. Поздно — `410 window_closed`. Черновик или
   отмена — `403 not_published`.
4. Ключ «этот браузер голосовал» уже есть — `409 already_voted`, кнопки не
   показываются.
5. Наружу уходят `id`, `name`, `closes_at` и `{key, label}`.
6. Новый `vid` попадает в `Set-Cookie`, только если обработчик дошёл до
   ответа: `HttpOnly`, `SameSite=Lax`, сутки, путь `/`. Страница cookie
   прочитать не может.

Текст ошибки зрителя берётся из `viewerMessages` в
`frontend/src/errorMessages.ts`. Пока запрос идёт, экран в `loading`.

### Нажатие

`submit(option)` ставит `submitting` и шлёт `{"option": "a"}`. `a` — это
`key`, не подпись на кнопке. `vote()` снова достаёт `vid` и IP, затем
`accept_vote()`:

1. ещё раз проверяет окно: между открытием и кликом оно могло закрыться;
2. нет такого ключа — `422 invalid_option`, Redis ещё не изменён;
3. считает SHA-256 от `question_id|viewer_id`, ключ
   `vote:123:<хеш>`;
4. выбирает шард `crc32(хеш) % COUNTER_SHARDS`, локально это
   `results:123:0`;
5. Lua в `vote/atomic_counter.py` атомарно ставит отметку и увеличивает
   счётчик;
6. скрипт вернул `0` — `409`; вернул `1` — собирается `VoteEvent`.

`VoteEvent` хранит номер вопроса, ключ варианта, хеш cookie, хеш IP и время.
Сырой IP не пишется: `client_ip_hash()` считает SHA-256 от `ip|соль`. Соль —
`IP_HASH_SALT`. Этот хеш в решение «пускать или нет» не входит. Два браузера
за одним роутером имеют один IP и разные cookie, оба голоса принимаются.

Redis выполняет скрипт целиком. Отметка уже есть — вернуть `0`. Ключ
счётчика должен отсутствовать или быть hash. Иначе скрипт падает и отметку
не ставит. Срок отметки — до конца окна плюс сутки. Затем `HINCRBY` на 1.

Две отдельные команды могли бы разорваться падением процесса. Один `eval`
этого разрыва не оставляет. Повтор после потерянного ответа получает
`already_voted`: счётчик уже увеличен один раз.

При `VOTE_ASYNC=false` строка журнала пишется сразу. При `VOTE_ASYNC=true`
событие встаёт в очередь процесса, пачка до 1000 строк или 50 мс.
`INSERT ... ON CONFLICT DO NOTHING` глушит повтор той же пары
`(question_id, dedup_key)`. Если запись журнала не удалась, голос в сумме
Redis уже есть. Это ограничение текущей версии, оно в
[roadmap](05-production-roadmap.md).

После `201` экран показывает успех. Следующее открытие с той же cookie
получит `already_voted`.

## Сценарий 3. Админ смотрит суммы

Ссылка ведёт на `/admin/questions/123`. `ResultsPage` вызывает
`GET /questions/123/results`. Пока статус `live`, запрос повторяется каждые
2 секунды.

`get_results()` в `backend/app/result/service.py`:

1. читает вопрос из PostgreSQL, чтобы знать подписи и статус;
2. одним pipeline читает все шарды `results:{id}:{n}` и складывает числа;
3. если хотя бы один шард непустой, это и есть ответ;
4. если полей нет и эфир уже кончился, `rebuild_results()` делает
   `GROUP BY` по `vote`, пишет снимок в `question_result` и кладёт числа
   обратно в Redis;
5. пока идёт эфир и счётчиков нет, пересчёт не запускается.

Проценты считает браузер: `count / total`. Принудительный пересчёт —
`POST /questions/{id}/results/rebuild`. Кнопки в интерфейсе нет.

## Что можно менять после создания

`update_question()` сравнивает пары `(key, label)`. Если они изменились,
`_has_votes()` смотрит строку в `vote` и положительные значения шардов.
Любой найденный голос даёт `409 options_locked`. Имя, время, длительность и
статус при тех же кнопках менять можно. После commit карточка в Redis
перезаписывается.

`delete_question()` удаляет только черновик без голосов. Остальное —
`409 delete_forbidden`. В таблице кнопка удаления и так выключена, если
статус не `draft`. После удаления ключ `question:{id}` стирается.

Кривой JSON, пустое имя, меньше двух вариантов или `published` без
`show_time` FastAPI ловит раньше сервиса и отдаёт `422 invalid_body`.
