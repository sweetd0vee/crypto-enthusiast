# ТЗ. Сервис минутного ТВ-опроса

## 1. Контекст

Ролик на федеральном канале длится около минуты. В кадре один вопрос (multiple choice, A/B или любое число вариантов) и QR. Ссылка живёт вместе с показом: до `show_time` голосовать нельзя, через `duration_seconds` (по умолчанию 60) вопрос перестаёт принимать ответы.

Ориентир нагрузки из условия: ролик смотрят ~100 млн человек, и в эту минуту они голосуют. Для сдачи тестового нужен локально запускаемый сервис с честной семантикой. Схема, которая выдерживает минутный всплеск, описана в архитектуре и должна быть видна в коде (счётчики, дедуп, пакетная запись), даже если на ноутбуке гоняем тысячи, а не миллионы запросов в секунду.

На каждый вопрос в обсуждении фигурирует порядок 10 млн сохранённых ответов. Итог для админки обязан считаться быстро и на этом объёме.

## 2. Роли

**Зритель.** Без регистрации открывает ссылку с QR, видит вопрос и варианты, отправляет один вариант.

**Админ.** Создаёт, меняет, удаляет опросы и смотрит обезличенные суммы. В тестовом админ — это статический токен в заголовке, не полноценный IAM.

## 3. В скоупе

1. Анонимный просмотр вопроса и один голос: `GET/POST /questionnaire/{id}`.
2. Отказ, если окно показа закрыто или ещё не началось.
3. Отказ повторного голоса с того же браузера.
4. CRUD вопроса с динамическим списком вариантов и статусом.
5. Обезличенный результат: сколько голосов у каждого варианта, без IP и без идентификаторов зрителей.
6. Локальный запуск (Docker Compose: API, PostgreSQL, Redis) и сценарий проверки curl-ами.
7. Описание сервиса, обоснование архитектуры, эти документы в репозитории.

## 4. Вне скоупа тестового

- Регистрация, профили, «правильный ответ», лидерборд (это модель референсного репозитория, не этого задания).
- Устойчивость к технически подкованной накрутке: боты, пул прокси, сброс cookie.
- Несколько вопросов в одном ролике. В ролике всегда один вопрос. «Опрос» в админке = одна запись `question` плюс её варианты.
- Полнотекстовый поиск, Elasticsearch, мультитенантность, биллинг.
- Продакшен-кластер Kubernetes. В документации фиксируем, как сервис ляжет в k8s, манифесты пишем только если останется время.

## 5. Функциональные требования

### 5.1 Зритель

Ссылка с QR: `/questionnaire/{id}`.

`GET` возвращает форму, если одновременно:

- вопрос существует и не отменён;
- `show_time <= now < show_time + duration`;
- с этого браузера по этому вопросу ещё не голосовали.

Иначе форма не отдаётся, приходит машинный код:

| Ситуация | Код | `error` |
| --- | --- | --- |
| Нет вопроса | 404 | `not_found` |
| Ещё рано | 403 | `window_not_started` |
| Минута вышла | 410 | `window_closed` |
| Уже голосовал | 409 | `already_voted` |
| Вопрос отменён или черновик | 403 | `not_published` |

`POST` с телом `{"option": "a"}`:

- те же проверки окна и дедупа;
- `option` обязан совпасть с ключом существующего варианта;
- успех — `201` и короткое подтверждение, без текущих процентов (проценты в прямом эфире стимулируют стадный эффект; в тестовом их можно отдать отдельным публичным флагом, по умолчанию выключен);
- повторный `POST` не увеличивает счётчик.

Идентификатор браузера — cookie `vid` (UUID). Если cookie нет, сервер выставляет его на `GET`. В журнал пишутся хеш cookie и хеш IP, время голоса, id вопроса и ключ варианта. Сырой IP в ответах API не отдаётся.

Время окна считает сервер. Время с телефона зрителя не используется.

### 5.2 Админ

Все маршруты ниже требуют `Authorization: Bearer $ADMIN_TOKEN`. Без токена — `401`.

Вопрос:

- `POST /questions` — создать;
- `GET /questions` — список;
- `GET /questions/{id}` — карточка с вариантами;
- `PUT /questions/{id}` — изменить текст, окно, варианты, статус;
- `DELETE /questions/{id}` — удалить черновик. Если уже есть голоса, удаление запрещено (`409`), доступна отмена статуса.

Варианты динамические: у A/B два элемента, у multiple choice — сколько передали (в тестовом лимит 2…10). Ключ варианта уникален внутри вопроса (`a`, `b`, … или произвольная короткая строка). Колонки `a/b/c/d` в таблице вопроса не используем: они ломаются на вопросе из двух или из пяти пунктов.

Поля создания:

- `name` — текст вопроса;
- `options[]` — `{ "key", "label" }`;
- `show_time` — момент, с которого ссылка принимает голоса (UTC);
- `duration_seconds` — по умолчанию 60, для локальной проверки можно поставить больше;
- `status` — `draft` или `published`. Черновик не виден зрителю. `cancelled` снимает вопрос с эфира.

Статусы `scheduled` / `live` / `closed` в базу отдельным воркером не пишем. Их вычисляем из `status`, `show_time` и `duration_seconds`, чтобы не гонять cron каждую секунду.

### 5.3 Результат

`GET /questions/{id}/results` (админ):

```json
{
  "question_id": 1,
  "name": "What is 100+8?",
  "effective_status": "closed",
  "total": 9001500,
  "counts": [
    {"key": "a", "label": "108", "count": 600},
    {"key": "b", "label": "102", "count": 900},
    {"key": "c", "label": "303", "count": 9000000},
    {"key": "d", "label": "20", "count": 8100}
  ]
}
```

Цифры берутся из Redis. Если ключей счётчиков нет (рестарт, истечение TTL), сервис один раз пересчитывает их из журнала `vote` и кладёт снимок в `question_result`. Пока идёт минутный эфир, дашборд не запускает `GROUP BY` по миллионам строк.

Публичного списка «кто как голосовал» нет.

## 6. Нефункциональные требования

- Окно и дедуп проверяются до увеличения счётчика. Два одновременных `POST` с одним `vid` дают ровно один голос (атомарный `SET NX`).
- Голос после `show_time + duration` не сохраняется, даже если форма была открыта заранее.
- Изменение вариантов у вопроса, по которому уже есть голоса, запрещено. Менять текст вопроса можно.
- Итог админки на горячем вопросе — чтение нескольких ключей Redis, не агрегация таблицы.
- Журнал `vote` партиционируется по `question_id`, чтобы один ролик не раздувал общую таблицу и чтобы старый эфир можно было отсоединить.
- Секреты только из окружения: `DATABASE_URL`, `REDIS_URL`, `ADMIN_TOKEN`.

## 7. Критерии приёмки тестового

Сервис считается сданным, когда по README его поднимает человек без устного пояснения и проходят сценарии:

1. Создать опубликованный вопрос с `show_time` в ближайшие секунды и четырьмя вариантами.
2. `GET /questionnaire/{id}` до `show_time` → `window_not_started` и без формы.
3. В окне `GET` отдаёт вопрос и варианты, без служебных полей админки.
4. `POST` с вариантом `a` → `201`, повтор с тем же cookie → `409`, счётчик `a` равен 1.
5. Второй cookie, тот же IP → второй голос принимается (NAT не склеивает людей).
6. `POST` с ключом не из списка → `422`.
7. После конца окна `POST` → `410`, счётчики не меняются.
8. `GET /questions/{id}/results` показывает суммы по ключам и `total`. Сумма по ключам равна `total`.
9. `PUT` и `DELETE` черновика работают. Удаление вопроса с голосами возвращает `409`.
10. Запрос результатов не содержит IP, cookie и хешей.

Плюс к сдаче, если останется время: фронт из [04-frontend-plan.md](04-frontend-plan.md), короткий k6-скрипт на локальный потолок, `docker-compose` одной командой.

## 8. Соответствие наброску с собеседования

| Набросок | Как ложится в ТЗ |
| --- | --- |
| `question`: id, name, a, b, c, d, show_time | `question` + таблица `question_option`. `show_time` и `duration_seconds` задают минуту |
| `answer`: questionId, answer, clientId | `vote`: question_id, option_key, хеш cookie, хеш IP, voted_at |
| clientId `0:0:0:0:0:0:0:1` как IPv6 | В референсе это id тенанта Auth0, не адрес зрителя. У нас зритель — cookie, IP только хеш в журнале |
| CRUD `POST/PUT /questions` | Сохраняем пути. Тело — JSON с массивом `options`, не четыре фиксированных поля |
| `/result/[questionId]` и группировка | `GET /questions/{id}/results`. Группировка сделана инкрементом при записи, не сканом `answer` |
| 10 млн записей на вопрос, «вопрос про скорость» | Счётчики Redis + пакетная запись журнала. Подробности в архитектуре |
