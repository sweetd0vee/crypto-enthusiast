# План реализации бэкенда

Порядок такой, чтобы после каждого шага был проверяемый результат. Шаги 1–7 закрывают приёмку из ТЗ. Шаг 8 — то, что отличает решение от CRUD «на оценку».

Репозиторий рядом с этими документами. Код, `docker-compose`, README и `docs/` коммитятся вместе. Скрывать, что спецификация собрана с ИИ, не нужно.

## Раскладка каталогов

Язык и библиотеки — в [стеке](06-stack.md): Python 3.12, FastAPI, Uvicorn, Pydantic v2, SQLAlchemy 2 Core, asyncpg, Alembic, redis-py.

```text

README.md                    # как поднять и прогнать сценарии приёмки

```

## Шаг 1. Каркас и локальный запуск

- `docker-compose.yml`: `postgres:16`, `redis:7`, сервис `api` с `DATABASE_URL`, `REDIS_URL`, `ADMIN_TOKEN`, `IP_HASH_SALT`, `COUNTER_SHARDS=1`.
- `GET /healthz` проверяет оба хранилища и отвечает `200`.
- README: `docker compose up --build`, затем переменные и базовый curl.

Готово, когда health зелёный на чистой машине с Docker.

## Шаг 2. Схема

Файл `migrations/001_init.sql` создаёт `question`, `question_option`, `vote`, `question_result` как в [архитектуре](02-architecture.md).

Ограничения сразу, не «потом»:

- `status` только из трёх значений;
- `duration_seconds` от 10 до 3600 (60 по умолчанию; нижняя граница, чтобы локальный тест не мигал);
- уникальность `(question_id, key)` у вариантов;
- уникальность `(question_id, dedup_key)` у голосов;
- `option` в журнале не FK на вариант: вариант нельзя удалить после голосов, но журнал не должен падать, если админ правил черновик до эфира. Проверка «такой ключ есть» делается в приложении до записи.

Готово, когда `alembic upgrade head` применяется повторно без ошибок.

## Шаг 3. CRUD вопросов

Эндпоинты из [контракта](05-api.md). Вся админка за одной функцией проверки токена.

Правила записи:

- создать можно `draft` или `published`;
- вариантов от 2 до 10, ключи уникальны, `label` не пустой;
- `show_time` обязателен для `published`;
- `PUT` заменяет набор вариантов целиком, если голосов ещё нет;
- если в `vote` или в Redis-счётчике уже есть голоса — менять `options` нельзя (`409 options_locked`);
- `DELETE` физический только для `draft` без голосов. Иначе `PUT` в `cancelled`.

Эффективный статус считается функцией `EffectiveStatus(q, now)` и отдаётся в JSON рядом с сохранённым `status`.

Кэш карточки в Redis писать здесь же: каждый успешный `POST`/`PUT`/`DELETE` обновляет или стирает `question:{id}`.

Готово, когда curl-сценарии создания, правки, списка, чтения и удаления черновика из приёмки проходят без фронта.

## Шаг 4. Публичное чтение формы

`GET /questionnaire/{id}` без токена.

- Берёт карточку из Redis, при промахе — из Postgres.
- Считает окно от серверных часов.
- Если cookie `vid` нет — выдаёт новый UUID.
- Если дедуп-ключ уже есть — `409`, форму не отдаёт.
- В JSON для зрителя только `id`, `name`, `options[{key,label}]`, `closes_at`. Без `status`-черновиков админки и без хешей.

Готово, когда до `show_time`, внутри окна и после окна ответы совпадают с таблицей кодов в ТЗ.

## Шаг 5. Приём голоса

`POST /questionnaire/{id}/votes`.

Порядок из архитектуры: публикация → окно → валидный `option` → `SET NX` → `HINCRBY` → запись журнала.

`dedup_key` и `ip_hash` считают в `internal/vote`, соль не логируют.

Синхронный `INSERT` в `vote` — путь по умолчанию для отладки. Рядом функция `enqueue(vote)`, которую обработчик вызывает при `VOTE_ASYNC=true`: буфер канала, воркер, пачка до 1000 строк или 50 мс, что наступит раньше. Уникальный индекс глушит дубль, если `SET NX` и вставка разошлись после рестарта: ошибку уникальности логируем и не откатываем счётчик задним числом в этой версии (редкий край; на защите проговариваем, что сверка — отдельная задача пересчёта).

Ответ `201`:

```json
{"status": "accepted", "question_id": 1, "option": "a"}
```

Готово, когда два параллельных `POST` с одним cookie оставляют `total = 1`, а два cookie с одного IP оставляют `total = 2`.

## Шаг 6. Результаты

`GET /questions/{id}/results` под токеном админа.

1. Прочитать все шарды `results:{id}:*`.
2. Если сумма нулевая и ключей нет — выполнить пересчёт из `vote`, записать `question_result` и прогреть Redis.
3. Сложить с подписями вариантов из карточки вопроса.
4. Ответ без идентификаторов зрителей.

Отдельный `POST /questions/{id}/results/rebuild` для админа: принудительный пересчёт. Нужен, чтобы на защите показать, откуда цифры, если Redis очистили.

Готово, когда после нескольких голосов суммы сходятся с числом строк в `vote`, а тело ответа не содержит `ip` и `dedup`.

## Шаг 7. Проверка приёмки и README

README на русском, коротко:

1. Требования: Docker. Python 3.12 нужен только если API запускают без контейнера.
2. `docker compose up --build`.
3. Токен админа из compose (для тестового — значение по умолчанию `dev-admin-token`, в проде так не оставляем).
4. Десять сценариев из раздела приёмки ТЗ — готовыми curl, с ожидаемым кодом.
5. Ссылка на `docs/` как на описание архитектуры.
6. Абзац, что спецификация и часть кода сделаны с Cursor, промпты и переписка лежат в репозитории как есть.

Автотесты на логику, которая легко ошибается:

- таблица `EffectiveStatus` на границах окна;
- отказ второго голоса (Redis — fakeredis, Postgres — по желанию в compose);
- запрет смены вариантов после голоса;
- сумма шардов.

Интеграционный тест одной командой `pytest`: httpx ходит в приложение через `ASGITransport`, Redis подменяется fakeredis. Если поднимать Postgres в тестах тяжело, достаточно fakeredis, юнитов окна и одного ручного прогона curl из README. Ручной прогон обязателен, его команды должны быть скопированы в README дословно.

## Шаг 8. Нагрузка, которую имеет смысл показать

Не обещать 1,7 млн RPS с ноутбука. Сделать три вещи, которые читаются за минуту:

1. Флаг `COUNTER_SHARDS` реально используется и при чтении, и при записи.
2. `VOTE_ASYNC` пачкой пишет журнал. Локально прогнать k6 или `hey` на `POST` и приложить в README порядок цифр своего ноутбука (RPS, p99), одной строкой, без графиков ради графиков.
3. В README отдельный подраздел «Что не влезает в один процесс»: шард счётчиков, память дедупа 8–16 ГБ на 100 млн, партиция `vote` на вопрос, несколько реплик API за балансировщиком, Redis Cluster. Это пересказ [архитектуры](02-architecture.md) на полэкрана, чтобы ревьюер увидел вывод без чтения всех docs.

Партицию по `question_id` добавлять в этом шаге, если журнал уже пишется пачкой. До шага 8 достаточно одной таблицы.

## Порядок коммитов

Имеет смысл коммитить по шагам, сообщениями вроде «добавить схему опросов и журнал голосов», «принять голос с дедупом в Redis». Так по истории видно, что сначала модель и CRUD, потом горячий путь, а не один свал-коммит.

## Что не делать в бэкенде

- Auth0, пользователи, лидерборд, поле правильного ответа.
- Elasticsearch.
- Очередь Kafka «для солидности». Канала в процессе на тестовом достаточно; в архитектуре сказано, куда он вырастет.
- Хранить сырой IP.
- Считать результаты `GROUP BY` на каждый `GET` дашборда.
