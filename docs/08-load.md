# Нагрузка

Верхний ориентир из [спецификации](01-specification.md) — 100 млн зрителей за
60 секунд одного ролика. Если явка близка к ста процентам, это около 1,7 млн
запросов в секунду на один `question_id`. Зритель делает короткий GET формы и
один POST голоса. Админка в эту минуту почти молчит.

Локальный контур эту цифру не воспроизводит. Код сохраняет форму горячего
пути: решение «принять голос» и оперативный итог живут в Redis, PostgreSQL
не участвует в этом решении.

## Что ломается при прямой записи в PostgreSQL

На таком пике каждый голос, проведённый через базу, упирается в одно и то же:

- уникальный индекс `(question_id, dedup_key)` сериализует проверку повтора
  на десятках миллионов строк;
- `GROUP BY` по журналу на каждый просмотр результата читает весь эфир;
- карточка вопроса читается из базы на каждый GET и POST;
- ответ зрителю ждёт commit строки журнала.

Поэтому в текущей реализации два профиля разведены. CRUD вопросов остаётся в
PostgreSQL. Голос и живые суммы проходят через Redis.

## Что уже делает код

| Узкое место | Как закрыто сейчас | Где |
| --- | --- | --- |
| Карточка на каждый запрос | JSON вопроса в Redis, ключ `question:{id}`. Промах читает PostgreSQL и прогревает кэш. `live` считается из времени сервера, отдельного cron нет | `question/cache.py`, `_load_question` |
| Дедуп | Ключ `vote:{id}:{sha256(question_id\|vid)}`, проверка за одно обращение. TTL — остаток окна плюс сутки | `vote/service.py`, `atomic_counter.py` |
| Два POST одного браузера | Один Lua: `EXISTS`, затем `SET EX` и `HINCRBY`. Между отметкой и счётчиком нет второго сетевого вызова | `atomic_counter.py` |
| Один ключ Redis на всю страну | Счётчик разбит на `results:{id}:{shard}`. Шард — `crc32(dedup_key) % COUNTER_SHARDS` | `_counter_shard` |
| Итог админки | Пайплайн `HGETALL` по числу шардов и сумма в процессе API. Число операций не растёт с числом голосов | `result/service.py` |
| Журнал на пути ответа | `VOTE_ASYNC=true`: очередь процесса, пачка до 1000 строк или 50 мс | `vote/journal.py` |
| Статика | Nginx отдаёт frontend и кэширует css/js. В API уходят только `/questionnaire` и `/questions` | `docker/nginx.conf` |
| Несколько реплик API | Процесс не хранит голоса и дедуп. Общий Redis принимает решение | `accept_vote` |

Локальные значения по умолчанию консервативные: `COUNTER_SHARDS=1`,
`VOTE_ASYNC=false`, Uvicorn запущен с `--workers 1`. Режим под пик включается
теми же переменными, отдельного сервиса для него нет.

## Путь одного голоса

`POST /questionnaire/{id}/votes` вызывает `accept_vote`:

1. Карточка берётся из Redis.
2. Окно и ключ варианта проверяются в процессе. Слишком ранний и слишком
   поздний запрос Redis не меняют.
3. Lua атомарно ставит дедуп и увеличивает один шард.
4. Повтор возвращает `409` и в журнал не попадает.
5. Принятый голос становится `VoteEvent`.
6. При `VOTE_ASYNC=true` событие кладётся в очередь, обработчик сразу отвечает
   `201`. При `VOTE_ASYNC=false` обработчик ждёт `INSERT`. Ошибка журнала
   пишется в лог, зрителю всё равно уходит `201`: счётчик Redis уже увеличен.

`GET` формы тоже идёт в Redis: карточка и `EXISTS` дедуп-ключа. Пока кэш
тёплый, публичные запросы PostgreSQL не открывают.

Если ответ Redis потерялся в сети, повтор того же `vid` получает
`already_voted`. Счётчик при этом увеличен один раз.

Пока Redis недоступен, голос получает `503`. Запасной `INSERT` в PostgreSQL
на этом пути не используется: без общего дедупа повтор перестал бы быть одним
голосом.

## Шарды счётчика

Redis выполняет команды одного ключа в одном потоке. Один hash на 1,7 млн
`HINCRBY` в секунду упирается в этот поток. `COUNTER_SHARDS` разносит записи
одного вопроса по нескольким ключам. Чтение складывает шарды обратно, админ
видит одну сумму.

Число шардов одинаково у всех реплик: ключ пишется и читается по одной
формуле. Смена числа не перекладывает уже накопленные ключи. Пересчёт из
журнала записывает снимок в шард `0`.

На одном экземпляре Redis скрипт трогает два ключа: дедуп и шард счётчика.
В Redis Cluster этим ключам нужен общий hash tag, иначе `EVAL` попадёт на
разные слоты. В текущих именах тега нет. Шарды рассчитаны на один Redis.
Кластер описан в [roadmap](05-production-roadmap.md) и в коде не включён.

Оценка памяти дедупа на 100 млн ключей — примерно 8–16 ГБ с учётом overhead.
Это оценка из [архитектуры](02-architecture.md), не результат прогона.

## Журнал

Очередь — `asyncio.Queue` на 10 000 событий и один worker на процесс. Пачка
уходит в PostgreSQL, когда набралось 1000 событий или прошло 50 мс.
`INSERT ... ON CONFLICT DO NOTHING` по `(question_id, dedup_key)` делает
повторную вставку той же пачки идемпотентной.

Полная очередь пишет в лог и отбрасывает событие. Счётчик Redis при этом уже
увеличен, строки в `vote` не появится. Очередь живёт в памяти процесса:
рестарт API теряет ещё не сброшенный batch.

Таблица `vote` разрезана на 16 hash-партиций по `question_id`. В минуту
ролика вопрос один, поэтому все строки этого эфира попадают в одну партицию.
Партиции отделяют разные вопросы друг от друга. Запись одного эфира они не
размазывают. Вынос очереди в Redis Stream и отдельные consumer — первый пункт
roadmap.

Пока вопрос `live`, просмотр результата не запускает `GROUP BY` по журналу.
Тяжёлый пересчёт бывает, когда счётчиков Redis нет и окно уже закрыто, либо
когда админ вызывает rebuild вручную.

## Что измерено

`backend/scripts/load_test.py` бьёт в локальный Docker отдельными cookie
`vid`. Контрольный прогон: 2000 принятых голосов, 1149,5 RPS, p95 117,2 мс,
p99 170,3 мс при `VOTE_ASYNC=true` и `COUNTER_SHARDS=4`. После прогона сумма
Redis совпала с числом строк журнала. Это один ноутбук и один процесс
Uvicorn.

Журнал одного эфира с индексами оценивается в десятки гигабайт. И эта оценка,
и цифры ноутбука не заменяют capacity-тест.

## Чего этот контур не закрывает

Код держит семантику пика: решение в Redis, журнал сбоку, итог за число
шардов. Пропускная способность 100 млн голосов в минуту не измерена.

Дальше, по [roadmap](05-production-roadmap.md):

- событие журнала в той же атомарной операции Redis, что дедуп и `HINCRBY`;
- отдельные consumer, очередь вне памяти процесса API;
- несколько реплик API за балансировщиком;
- Redis Cluster с общим hash tag на ключи одного `EVAL`;
- k6, запас ёмкости и проверка отказа Redis и consumer.
