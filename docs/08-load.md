# Нагрузка

Ориентир из [спецификации](01-specification.md) — 100 млн зрителей за 60
секунд одного ролика. При явке около 100% это примерно 1,7 млн RPS на один
`question_id`. Зритель делает короткий GET и один POST. Админка в эту минуту
молчит.

Локальный контур эту цифру не воспроизводит. Решение «принять голос» и
живой итог живут в Redis. PostgreSQL в этом решении не участвует.

## Почему не писать голос сразу в PostgreSQL

На таком пике каждый голос через базу упирается в одно и то же:

- уникальный индекс `(question_id, dedup_key)` сериализует проверку повтора;
- `GROUP BY` по журналу на каждый просмотр результата читает весь эфир;
- карточка вопроса читается из базы на каждый GET и POST;
- ответ ждёт commit строки журнала.

CRUD вопросов остаётся в PostgreSQL. Голос и живые суммы идут через Redis.

## Что горячий путь уже не делает

| Узкое место | Как закрыто | Где |
| --- | --- | --- |
| Карточка на каждый запрос | JSON в `question:{id}`. Промах читает PostgreSQL и прогревает кэш. `live` считается из времени сервера | `question/cache.py`, `_load_question` |
| Дедуп | `vote:{id}:{sha256(question_id\|vid)}`. TTL — остаток окна плюс сутки | `vote/service.py`, `atomic_counter.py` |
| Два POST одного браузера | Один Lua: `EXISTS`, затем `SET EX` и `HINCRBY` | `atomic_counter.py` |
| Один ключ Redis на страну | `results:{id}:{shard}`, шард — `crc32(dedup_key) % COUNTER_SHARDS` | `_counter_shard` |
| Итог админки | Один pipeline `HGETALL` и сумма в процессе. Число операций не растёт с числом голосов | `store/counter_shards.py` |
| Журнал на пути ответа | `VOTE_ASYNC=true`: очередь процесса, пачка до 1000 строк или 50 мс | `vote/journal.py` |
| Статика | Nginx отдаёт frontend. В API уходят `/questionnaire` и `/questions` | `docker/nginx.conf` |
| Несколько реплик API | Процесс не хранит голоса. Решение принимает общий Redis | `accept_vote` |

Локально `COUNTER_SHARDS=1`, `VOTE_ASYNC=false`, Uvicorn с одним worker.
Режим под пик включается теми же переменными, отдельного сервиса нет.

## Путь одного POST

1. Карточка берётся из Redis.
2. Окно и ключ варианта проверяются в процессе и Redis не меняют.
3. Lua атомарно ставит дедуп и увеличивает один шард.
4. Повтор возвращает `409` и в журнал не попадает.
5. Принятый голос становится `VoteEvent`.
6. При `VOTE_ASYNC=true` событие кладётся в очередь, ответ `201` уходит
   сразу. При `VOTE_ASYNC=false` обработчик ждёт `INSERT`. Ошибка журнала
   пишется в лог, зрителю всё равно уходит `201`: счётчик уже увеличен.

Пока кэш тёплый, публичные запросы PostgreSQL не открывают. Потерянный
ответ Redis безопасен: повтор того же `vid` получает `already_voted`.

Пока Redis недоступен, голос получает `503`. Запасного `INSERT` нет.

## Шарды и журнал

Один hash на 1,7 млн `HINCRBY` в секунду упирается в поток одного ключа.
`COUNTER_SHARDS` разносит записи. Чтение складывает шарды обратно. Число
шардов одинаково у всех реплик: смена числа не перекладывает уже
накопленные ключи. Пересчёт из журнала пишет снимок в шард `0`.

На одном Redis скрипт трогает два ключа: дедуп и шард. В кластере им нужен
общий hash tag, иначе `EVAL` попадёт на разные слоты. В текущих именах тега
нет. Оценка памяти дедупа на 100 млн ключей — примерно 8–16 ГБ. Это оценка,
не прогон.

Очередь — `asyncio.Queue` на 10 000 событий и один worker на процесс.
Полная очередь отбрасывает событие, счётчик Redis уже увеличен. Рестарт API
теряет несброшенный batch. `vote` разрезан на 16 hash-партиций по
`question_id`, но один эфир попадает в одну партицию.

Пока вопрос `live`, просмотр результата не запускает `GROUP BY`. Тяжёлый
пересчёт бывает, когда полей в шардах нет и окно закрыто, либо когда админ
вызывает rebuild.

## Что измерено

`backend/scripts/load_test.py` бьёт в локальный Docker отдельными cookie.
Контрольный прогон: 2000 принятых голосов, 1149,5 RPS, p95 117,2 мс,
p99 170,3 мс при `VOTE_ASYNC=true` и `COUNTER_SHARDS=4`. После прогона сумма
Redis совпала с числом строк журнала. Это один ноутбук и один процесс
Uvicorn.

Журнал одного эфира с индексами оценивается в десятки гигабайт. Ни оценка,
ни цифры ноутбука не заменяют capacity-тест. Что для него ещё нужно —
в [roadmap](05-production-roadmap.md).
