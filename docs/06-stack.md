# Технологический стек

Реализация: бэкенд на Python, фронт на React. Контракт API от языка не зависит и описан в [05-api.md](05-api.md). Здесь — конкретные фреймворки и зачем каждый в этой задаче.

Версии фиксируем в `pyproject.toml` и `web/package.json` на момент реализации. Ниже — выбор семейства, не номер патча.

## Сводка

| Слой | Выбор | Не берём |
| --- | --- | --- |
| API | Python 3.12, FastAPI, Uvicorn, Pydantic v2 | Django, Flask, Go |
| Данные | PostgreSQL 16, SQLAlchemy 2 (Core), asyncpg, Alembic | Elasticsearch, MongoDB |
| Горячий путь | Redis 7, redis-py (asyncio) | Kafka, RabbitMQ |
| Фронт | React 18, TypeScript, Vite, React Router | Next.js, Redux, UI-кит |
| Запуск | Docker Compose | Kubernetes в составе сдачи |
| Проверка | pytest, httpx, fakeredis, curl | отдельный нагрузочный стенд как обязательство |

Узкое место минутного эфира — Redis и журнал в Postgres, не фреймворк. Python здесь уместен: вакансия backend на Python, а счётчики и `SET NX` всё равно живут в Redis.

## Бэкенд

### Python 3.12

Базовый образ `python:3.12-slim`. Типы в сигнатурах сервисов (`question`, `vote`, `result`) обязательны: граница окна и дедуп легко ломаются, аннотации это ловят до рантайма.

### FastAPI

Один процесс отдаёт и админский CRUD, и публичное голосование. FastAPI даёт:

- разделение роутеров `admin` и `public` без самописного диспетчера;
- зависимости: проверка `Authorization: Bearer` на админских маршрутах и пустая зависимость на голосе;
- схемы запроса и ответа через Pydantic, код `422 invalid_body` на кривом JSON получается из валидации, а не ручным разбором;
- OpenAPI на `/docs` — ревьюер смотрит контракт рядом с curl из README.

Django и Django REST Framework не используем. Админка Django рисует таблицы сама и тянет сессии, пользователей и ORM на каждый запрос. Нам нужен тонкий JSON API и отдельный React. Лишняя админка разойдётся с контрактом.

Flask не используем. Голос — это несколько обращений в Redis и ответ без ожидания пачки INSERT. Это естественно ложится на `async def`. Во Flask то же самое пришлось бы собирать вручную.

### Uvicorn

ASGI-сервер для локального запуска и для контейнера: `uvicorn app.main:app --host 0.0.0.0 --port 8080`.

Один воркер в Docker Compose, чтобы фоновая очередь журнала (`asyncio.Queue` при `VOTE_ASYNC=true`) жила в том же процессе, что и обработчики. Несколько воркеров Uvicorn без внешней очереди размажут журнал по процессам и потеряют его при рестарте. Горизонтально API масштабируется копиями контейнера: дедуп и счётчики в общем Redis, своего состояния у воркера нет. Это тот же тезис, что в [архитектуре](02-architecture.md).

### Pydantic v2

Модели тела `POST /questions`, голоса `{"option": "a"}` и ответов результатов. Валидация: 2–10 вариантов, уникальные `key`, непустые `label`, `duration_seconds` в допустимых границах. Наружу отдаём поле `error` из [контракта](05-api.md), а не сырой `detail` FastAPI: для этого один обработчик `RequestValidationError`.

### SQLAlchemy 2 и asyncpg

Драйвер — asyncpg. Доступ — SQLAlchemy 2 Core, не классические ORM-сессии на горячем пути.

- Вопросы и варианты: обычные `insert` / `update` / `select`. Их мало.
- Журнал `vote`: multi-row `INSERT` пачкой из фоновой задачи. Core это выражает прямо, без идентичности объектов на 10 млн строк.
- Пересчёт результатов: тот самый `GROUP BY option_key`, только из `POST .../results/rebuild` и при пустом Redis.

Полноценный ORM-слой с ленивыми связями здесь вреден: легко случайно прочитать варианты отдельным запросом на каждый голос.

### Alembic

Миграции схемы из [архитектуры](02-architecture.md): `question`, `question_option`, `vote`, `question_result`. Каталог `migrations/`. На старте compose миграция применяется до приёма трафика.

### redis-py

Клиент `redis.asyncio`. Три использования, все в одном инстансе Redis 7:

- `SET key NX EX` — дедуп cookie;
- `HINCRBY` / `HGETALL` — шарды счётчиков `results:{questionId}:{shard}`;
- строка JSON — кэш карточки вопроса.

Пул соединений создаётся в lifespan FastAPI и закрывается при остановке. Если Redis на `POST` голоса недоступен, ответ `503`, в Postgres по одному голосу не пишем.

### Очередь журнала

Отдельный брокер не поднимаем. При `VOTE_ASYNC=true` обработчик кладёт событие в `asyncio.Queue`, фоновая задача раз в 50 мс или каждые 1000 событий делает один `INSERT`. Для тестового синхронная вставка остаётся режимом по умолчанию, флаг показывает границу, за которой INSERT уходит из запроса зрителя.

### Конфигурация

`pydantic-settings`: `DATABASE_URL`, `REDIS_URL`, `ADMIN_TOKEN`, `IP_HASH_SALT`, `COUNTER_SHARDS`, `VOTE_ASYNC`. Секретов в коде нет.

### Логи и качество

- логи — стандартный `logging` в JSON-подобной строке, без отдельного стека наблюдаемости;
- линтер и формат — Ruff;
- тесты — pytest, pytest-asyncio, httpx (`ASGITransport` по приложению без открытого порта), fakeredis для `SET NX` и шардов. Postgres в юнитах не обязателен: окно и дедуп проверяются на fakeredis и чистых функциях. Полный сценарий приёмки — curl из README против compose.

Раскладка:

```text

app/config.py                # pydantic-settings
app/api/public.py            # /questionnaire

app/api/errors.py            # единый JSON ошибки

app/vote/service.py          # окно, дедуп, счётчик, очередь

app/store/redis.py

```

## Фронтенд

Каталог `frontend/`. Подробный состав экранов — в [плане фронта](04-frontend-plan.md).

### React 18 и TypeScript

Два экрана: форма с телефона и админская таблица. TypeScript нужен на границе с API: коды `window_closed`, `already_voted`, `options_locked` — это дискриминируемый набор, а не строка «что-нибудь». React 18 без серверных компонентов: данные приходят с уже готового API, рендерить страницу на сервере незачем.

### Vite

Сборка и dev-сервер. Прокси `/questionnaire` и `/questions` на `http://localhost:8080`, чтобы cookie `vid` была same-site. Фронт cookie не читает и не генерирует.

### React Router

Маршруты `/q/:id`, `/admin`, `/admin/login`, `/admin/questions/:id`. Вложенных лейаутов и загрузчиков данных из роутера достаточно не будет — страницы сами вызывают `fetch`. React Router берём только как таблицу путей.

### Запросы

Обычный `fetch`. Для админки тонкая обёртка добавляет `Authorization` из `sessionStorage`. Отдельный клиент (axios) не нужен: эндпоинтов мало, тело ошибок одно.

Состояние сервера живёт в компоненте страницы. Redux, Zustand и React Query не подключаем. Единственный повторный опрос — `GET /questions/{id}/results` раз в 2 секунды, пока вопрос в эфире. Это `setInterval` на одной странице.

### Чего нет во фронте

- Next.js. Два маршрута не окупают серверный рантайм, а QR-страница и так статическая оболочка над API.
- Готовый UI-кит (MUI, Ant Design). Кнопки варианта и таблица вопросов собираются своими стилями, чтобы сдача не зависела от темы чужой библиотеки.
- Websocket и SSE. Агрегат уже посчитан на бэкенде, опроса раз в две секунды хватает.

Скрипты: `npm run dev` для проверки, `npm run build` чтобы убедиться, что типы сходятся. Node — текущий LTS, фиксируется в `web/package.json` через `engines` только если без этого сборка плавает.

## Инфраструктура локального запуска

`docker-compose.yml`:

| Сервис | Образ | Зачем |
| --- | --- | --- |
| `postgres` | `postgres:16` | вопросы, журнал, снимок итога |
| `redis` | `redis:7` | дедуп, счётчики, кэш карточки |
| `api` | сборка из `Dockerfile` на `python:3.12-slim` | Uvicorn на порту 8080 |

Фронт в compose не обязателен: на защите его поднимают отдельно через Vite, API уже отвечает на curl. Так падение страницы не маскирует неготовый бэкенд.

Прод-контур компании (Kubernetes, несколько реплик API, Redis Cluster) в манифестах тестового не собираем. В README остаётся короткий абзац, как процесс без состояния ложится в несколько реплик. Elasticsearch в стек не входит: итог — суммы по ключам вариантов, не поиск.
